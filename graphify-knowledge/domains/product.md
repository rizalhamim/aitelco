## Approved agent key facts

- revenue (FLOAT, IDR) is the metric - always SUM; /1e6=Mn, /1e9=Bn. hit=transaction count; ARPT=SUM(revenue)/SUM(hit).
- Product dimensions (broad->narrow): kpi_group (3: REVENUE DATA/NON DATA/PPU DATA) -> service_type -> kpi (stream) -> family_group (family/campaign) -> product_group (specific SKU).
- family_group examples: FREEDOM INTERNET (FI/FIS), HAPPY, CVM PACK, PAYU, RAMADAN SATSPAM+, VAS, DATA LOAN PACK, ROAMING.
- kpi examples: REVENUE MOBO, DATA ORGANIC, REVENUE ORGANIC, EWALLET, REVENUE EVC, VOUCHER ORI/NON-ORI, VAS, REVENUE RITA, LOAN PACKAGE/FEE, VOICE, SMS.
- kpi_group REVENUE DATA dominates (~94%); use it for a quick data vs non-data split.
- validity=package days (28/45/7/3...), quota_data=GB; segment sachet (short) vs monthly (28-30D).
- month_id is STRING 'YYYYMM' (compare as strings); dt_id is DATE. brand only IM3 or 3ID. channel_group: ORGANIC / DIGITAL DISTRIBUTION / MOBO TRADE.
- Tables: _daily (dt_id, ~4B rows, filter date+territory!), _mtd (month_id MTD), _mth (month_id full, 39 months).
- FWA / HiFi Air: family_group = '09. FWA' (also a small 'SP FWA' family). 'unlimited' FWA = product_group = 'HIFI AIR UNLIMITED'. Other FWA SKUs are 'HIFI AIR BULANAN <N>GB', 'HIFI AIR 90GB', etc. 'hit' = transaction/recharge count; SUM(hit) for volume.
- SCAN-CAP RULE for rham_site_data_rev_product_mth (wide, ~39 months, site-grain): always pin month_id to an EXACT value, e.g. month_id='202605' (May) - do NOT use month_id LIKE '%05' (scans all years and blows the 50 GB cap). SELECT only the needed columns (e.g. SUM(hit)) and add territory filters (kabkota / kecamatan / circle). The kab/kota column here is 'kabkota' (WITH 'a'). For full-month figures use _mth; for MTD use _mtd.
- PARTITION PRUNING: BigQuery can only prune partitions on a LITERAL filter value. Writing the latest period as `month_id = (SELECT MAX(month_id) ...)` or as a JOIN to a MAX() CTE defeats pruning and scans EVERY month (measured on rham_site_data_rev_product_mth: 45.0 GB dynamic vs 1.6 GB literal, so the dynamic form trips the 50 GB cap). Use a literal, e.g. month_id = '202608' (or an IN list of exact months for MoM/YoY). The current month_id is in the domain facts; never compute it inside the same query you are filtering.
