  #   Agent                Model Variable    Saat Ini              Tugas Utama
  --- -------------------- ----------------- --------------------- ----------------------------------
  1   Analyst Agent        LLM_MODEL_FAST    Agent-Java-v02.3      Validasi intent, rephrasing
  2   Orchestrator/Router  LLM_MODEL_FAST    Agent-Java-v02.3      Routing ke domain yang tepat
  3   SQL Agent            LLM_MODEL         Agent-Java-v02.3      Generate BigQuery SQL
  4   Synthesizer          LLM_MODEL         Agent-Java-v02.3      Merangkai jawaban dari data
  5   Profile Planner      LLM_MODEL_FAST    Agent-Java-v02.3      Merencanakan profile deck
  6   Profile Compiler     LLM_MODEL         Agent-Java-v02.3      Menyusun narrative profile
  7   Export Agent         (Tidak pakai LLM)  -                    Generate XLSX/PDF

  Catatan: Saat ini SEMUA agent pakai model yang SAMA (Agent-Java-v02.3).
  Ini tidak optimal — agent routing/classification tidak perlu model berat.

Pipeline Flow:
  User -> Analyst -> Router -> [SQL Agent -> BigQuery -> Synthesizer] -> User
                            -> [Profile: Planner -> Parallel SQL -> Compiler] -> User
                            -> [General Reply langsung] -> User
                            -> [Export Agent (no LLM)] -> File download

Jumlah LLM call per request:
  - Chat biasa (greeting):       2-3 calls
  - Data query standar:          4 calls (analyst + router + SQL + synthesizer)
  - Profile deck lengkap:        15-25 calls (analyst + router + planner + ~11 SQL + compiler)

TUGAS:

AGENT #3: SQL AGENT (Text-to-SQL)
================================================================================

File:           backend/app/orchestrator.py -> write_sql()
Model:          LLM_MODEL (saat ini: Agent-Java-v02.3)
Max Tokens:     2500
Streaming:      Tidak (JSON response)
Call Method:    llm.chat_json()
Self-Correct:   Ya, hingga 3 percobaan (error + prior SQL dikirim balik)

TUGAS:
  - Agent PALING KRITIKAL — menghasilkan BigQuery Standard SQL dari pertanyaan
  - Menerima schema tabel spesifik untuk domain yang dipilih Router
  - Menggunakan data_facts untuk context (date ranges, brand names, dll)
  - Harus menghasilkan query yang aman (read-only, bounded cost, LIMIT)
  - Self-correction: jika SQL error, menerima error message dan SQL sebelumnya, lalu memperbaiki

INPUT:
  - System prompt (IDENTITY + domain-specific schema + data_facts + hard rules)
  - Optional: previous turn context (domain, SQL, columns, sample rows)
  - 4 message history terakhir
  - User question (+ prior_error & prior_sql jika retry)

OUTPUT (JSON):
  {
    "sql": "SELECT ... FROM `data-java-prd-97b9.java_precalc.table` WHERE ...",
    "explanation": "Query ini menghitung total revenue prepaid per kecamatan..."
  }

KNOWLEDGE (sangat kaya — ini yang membedakan agent ini):
  1. schema_for_domain(domain_key):
     - Semua tabel di domain dengan deskripsi
     - Hingga 35 kolom per tabel dengan tipe data
     - Kolom tersembunyi (nama saja) jika lebih dari 35
  2. data_facts_text():
     - Date ranges aktif per tabel (misal: "rham_site_wise_daily: 2024-01-01 to 2025-05-28")
     - Brand names: ["im3", "3id", "tsel", "xl", "sf", "by.u"]
     - Territory hierarchy: kec -> kabkota -> province -> region -> circle -> national
     - Common column patterns dan naming conventions
  3. Hard rules di prompt:
     - Fully-qualified table names wajib
     - Partition filter wajib
     - month_id harus di-CAST ke STRING sebelum math
     - Window function tidak boleh di WHERE/HAVING/JOIN ON
     - Revenue default = rev_prepaid
     - Causal analysis: Akuisisi -> Subscriber -> Usage -> Revenue

TABEL YANG DITANGANI:
  Semua tabel di domain yang dipilih Router. Contoh:
  - site_performance: 17 tabel (873M+ rows terbesar)
  - marketing: 3 tabel (160+ kolom per tabel)
  - reporting: 27 tabel (pre-aggregated market share)
  - network: 13 tabel (5G, availability, OpenSignal)
  - geo: 8 tabel (branch, desa, territory)

KONEKSI KE AGENT LAIN:
  - Input dari: Router (domain) + Analyst (validated_query + hints)
  - Output SQL -> BigQuery Tool (run_query)
  - Output explanation -> Synthesizer (context)
  - Retry loop: BigQuery error -> SQL Agent (self-correct) -> BigQuery (max 3x)

REKOMENDASI MODEL:
  Butuh: Akurasi SQL TINGGI, pemahaman schema kompleks, self-correction
  -> claude-3.5-sonnet atau claude-sonnet-4 (SQL accuracy terbaik)
  -> gpt-4o (SQL sangat baik, sedikit lebih cepat)
  -> JANGAN pakai model kecil — SQL errors costly (3 retry = 3x latency + 3x cost)

  JANGAN: gpt-4o-mini, gemini-flash — terlalu banyak SQL error

UNTUK NARASI / SYNTHESIS (Synthesizer, Profile Compiler):
  Ranking:
